Referencia HTTP para conectar el ERP

El bot de asistencias es el sistema de registro (Discord + MySQL). El ERP es un cliente HTTP: lee datos y cambia configuración / estado. El bot no llama al ERP para marcar entrada o salida.

Base URLhttps://mtaasistenciabot-production.up.railway.app
Prefijo/api/v1
FormatoJSON UTF-8 · Content-Type: application/json
CORSAbierto (Access-Control-Allow-Origin: *). Preflight OPTIONS → 204.
Zona horaria de negocioAmerica/Lima (fechas de jornada en calendario local)
Versión del bot2.2.0 (campo version en health / estado)

1. Modelo de integración

  • Fuente de verdad: MySQL del bot (Hostinger). Sheets es respaldo de emergencia, no API.
  • Quién escribe asistencias: Discord (botones Entrada / Salida). El ERP no registra marcaciones por esta API.
  • Quién lee: el ERP consume practicantes, jornadas (con horas de marca), horarios, marcaciones, resumen, ranking y config.
  • Quién opera el bot: el ERP puede poner el bot en mantenimiento / desactivado y editar variables de config_sistema.

Convención de nombres: la mayoría de payloads usan snake_case. GET /practicantes y GET /jornadas hoy devuelven camelCase (campos tal cual salen del servicio). El ERP debe mapear ambos.

2. Autenticación

Todos los endpoints salvo health y la raíz / exigen API key.

Enviar una de estas cabeceras (el valor es BOT_API_KEY de Railway):

x-api-key: TU_BOT_API_KEY

Authorization: Bearer TU_BOT_API_KEY
401Key ausente, distinta o de longitud distinta (comparación timing-safe).
503El bot arrancó sin BOT_API_KEY.

No hay JWT, OAuth ni scopes. Quien tenga la key tiene acceso de lectura y a los PUT/POST/PATCH/DELETE documentados.

3. Errores

Cuerpo unificado:

{
  "error": { "code": 401, "message": "API Key ausente o inválida." }
}
400Parámetro o JSON inválido.
401Sin credencial válida.
404Ruta, practicante, área o snapshot inexistente.
409El bot ya está en ese estado con el mismo mensaje.
422Regla de negocio (fecha pasada, config inválida).
500Error interno.
503Health degradado, o API key no configurada en el proceso.

8. Cliente mínimo (TypeScript / fetch)

const BASE = "https://mtaasistenciabot-production.up.railway.app";
const KEY = process.env.BOT_API_KEY!;

async function botGet(path: string) {
  const res = await fetch(`${BASE}${path}`, {
    headers: { "x-api-key": KEY },
  });
  const json = await res.json();
  if (!res.ok) throw Object.assign(new Error(json.error?.message ?? res.statusText), { status: res.status, json });
  return json;
}

async function botSend(method: string, path: string, body?: unknown) {
  const res = await fetch(`${BASE}${path}`, {
    method,
    headers: { "x-api-key": KEY, "Content-Type": "application/json" },
    body: body ? JSON.stringify(body) : undefined,
  });
  const json = await res.json();
  if (!res.ok) throw Object.assign(new Error(json.error?.message ?? res.statusText), { status: res.status, json });
  return json;
}

// Lectura
const activos = await botGet("/api/v1/practicantes?estado=activo");
const kevin = await botGet("/api/v1/practicantes/9/resumen?periodo=mes");

9. Fuera de alcance en esta API (especificado, no implementado)

La spec ESPEC-ASIS-001 describe un ERP más amplio. El bot no expone aún estos recursos. No los invoquéis: responderán 404 Ruta no encontrada.

GrupoRutas previstas, no vivas
Auth JWTPOST /auth/token, /auth/refresh
Marcaciones writePOST /marcaciones (el listado GET sí existe)
CRUD practicantesPOST /practicantes, PATCH /practicantes/{id}
Horarios writeasignaciones, excepciones (el GET de bloques sí existe)
Justificaciones / recuperacionesPOST sobre jornada, pendientes
Reportes extradiario, semanal, mensual, export xlsx/pdf
Webhooks salientesel bot no notifica al ERP; el ERP hace polling
Historial estado writePOST/PATCH/DELETE de historial (solo GET)

Si el ERP necesita alta de practicantes o justificar faltas, hay que ampliar esta API o hacerlo en MySQL / Discord. No hay puente oculto.
